### Frontend setup

**Required tools:** Android Studio, JDK 17, Android SDK Platform 35, Android SDK Platform-Tools, and Android Emulator. The project uses Kotlin 2.1.21, Android Gradle Plugin 8.13.2, and the supplied Gradle wrapper. The minimum Android API level is 26; compile and target SDK levels are 35.

**Configuration:** Clone the repository and open its `frontend` directory in Android Studio. Create `frontend/local.properties` using `frontend/local.properties.example` as a reference. Keep the SDK path generated by Android Studio, and add the following deployment settings:

```properties
sdk.dir=C:/Users/YOUR_WINDOWS_USERNAME/AppData/Local/Android/Sdk
API_BASE_URL=https://34.118.132.0
GOOGLE_CLIENT_ID=1088832067982-sp9vu1tvf1ohmq0j8l63eegdbvdvtfrq.apps.googleusercontent.com
```

Use the actual SDK location shown in Android Studio's SDK Manager. The Google client ID above is the Web OAuth client ID configured in the development checkout. The backend must use the same Web client ID. 

Both `API_BASE_URL` and `GOOGLE_CLIENT_ID` are embedded in the APK at build time, so changing them requires rebuilding the app.

**Build and run in Android Studio:**

1. Open **File > Settings > Build, Execution, Deployment > Build Tools > Gradle** and select **JDK 17** as the Gradle JDK. On macOS, open settings through **Android Studio > Settings**.
2. Select **File > Sync Project with Gradle Files**. Install any missing SDK components requested during synchronization.
3. Open **View > Tool Windows > Device Manager** and create or start a **Pixel 9** emulator with **Android 16 / API 36** and Google services. A Google Play system image supports adding a Google account for the login test.
4. Open **View > Tool Windows > Build Variants** and select **debug** for the `app` module.
5. Select the **app** run configuration and the emulator in the toolbar, then click **Run**. Android Studio builds, installs, and launches the app. Build errors appear under **View > Tool Windows > Build**.

### Backend setup

The backend uses Node.js 22, TypeScript, Express, and `ws`. Docker builds it from `backend/Dockerfile`. Install Docker Engine/Desktop with **Docker Compose v2.24 or newer**.

Create `backend/.env` from `backend/.env.example` and set:

```dotenv
PORT=3000
NODE_ENV=development
GOOGLE_CLIENT_ID=1088832067982-sp9vu1tvf1ohmq0j8l63eegdbvdvtfrq.apps.googleusercontent.com
```

No Google OAuth client secret, trivia API key, database seed, or application password is required by the current implementation. 

**Run locally:** Start Docker, then run these commands from the repository root:

```sh
docker compose up --build -d
docker compose ps
docker compose logs --tail=50 backend
```

Open [http://localhost:3000/health](http://localhost:3000/health) to check for `{"status":"ok"}`.

For an Android emulator to reach this local server, rebuild with `API_BASE_URL=http://10.0.2.2:3000`. However, `/server/ip` depends on GCP metadata and returns HTTP 503 outside GCP; the complete Login + Server information screen therefore requires the cloud backend.

After backend source changes, rebuild the container with `docker compose up --build -d backend`.

**Recreate the cloud deployment:** Use a Debian Compute Engine VM with an external IP and Docker installed. Clone the submitted version of this repository onto the VM and create `backend/.env` as above. Allow inbound TCP 80 and 443 in the GCP firewall and keep outbound access available for Google, certificate issuance, and the course WebSocket.

The following configuration is for a fresh deployment on the VM; these files are not included separately in this repository. Caddy handles HTTPS/WSS and proxies traffic to the backend. Replace `34.118.132.0` with the new VM's IP if deploying a different server, and update the frontend base URL accordingly.

Create `Caddyfile` at the repository root:

```caddyfile
{
    default_sni 34.118.132.0
}

https://34.118.132.0 {
    tls {
        issuer acme {
            dir https://acme-v02.api.letsencrypt.org/directory
            profile shortlived
        }
    }
    reverse_proxy backend:3000
}
```

This requests an IP certificate using Let's Encrypt's short-lived profile. Caddy manages renewal; preserve its data volume.

Create `compose.cloud.yml` at the repository root. This standalone configuration runs the M1 backend and TLS proxy.

```yaml
name: cpen321-m1-cloud

services:
  backend:
    build: ./backend
    restart: unless-stopped
    env_file:
      - ./backend/.env
    ports:
      - "127.0.0.1:3000:3000"
  caddy:
    image: caddy:2.11.2-alpine
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data
      - caddy-config:/config
    depends_on:
      - backend

volumes:
  caddy-data:
  caddy-config:
```

On a fresh VM, run from the repository root:

```sh
sudo docker compose -f compose.cloud.yml up --build -d
sudo docker compose -f compose.cloud.yml logs --tail=50 caddy
curl --fail-with-body https://34.118.132.0/health
curl --fail-with-body https://34.118.132.0/server/ip
```

Allow certificate issuance to complete before checking HTTPS. Keep using `-f compose.cloud.yml` for this deployment's subsequent commands.

### Button 3 Functionality 

The user enters a non-negative integer number of minutes and a seconds value from 0 to 59, then selects **Start timer**. The total duration must be positive. The app displays the remaining seconds and prevents another timer from starting while the current timer is running. Switching between the menu, login screen, pixel grid, and timer does not stop the countdown while the app remains active.

When the countdown reaches zero, a dialog requests one Science: Computers multiple-choice question directly from Open Trivia Database:

```text
https://opentdb.com/api.php?amount=1&category=18&type=multiple&encode=base64
```

The app decodes the Base64 question and answers, combines the correct answer with the incorrect options, and shuffles their order. After one selection, the answer buttons are disabled. A correct answer displays encouragement to keep learning; an incorrect answer reveals the correct answer. The user can close the dialog and start another timer.

The dialog displays a loading state while fetching the question. If the request fails, it shows an error and a **Retry** action that waits five seconds before trying again.

## AI Use Reflection

### Tasks 
1. Interactive learning
    - Description: Quickly get up to speed on various aspects of Android fullstack development through intensive interaction with AI, including setting up Android Studio, learning about Kotlin language features, backend deployment, and more.
    - AI interfaces and models used: Codex conversation as interface; GPT-5.6 Luna high, GPT-6 Astra high as models.
    - Strategy: Before I started working on M1, I had the AI model break M1 down into individual basic task blocks (such as “Create a button in the Blank app,” “Add an input field to the Timer page,” and so on). I then had the AI model ask me questions (such as what code to write, which Kotlin features to use, etc.), and after I provided my answers, it evaluated and corrected them. After I provided my answers, the AI would evaluate and correct them, and provide its sample code. In addition, after completing a major feature with the AI’s help (such as finishing the functionality of one button), I would ask the AI to provide me with some multiple-choice and short-answer quizzes to enhance my memory.
    - Advantages: Interacting with AI allowed me to complete a crash course in Android development in a short period of time and gain the ability to write and review Kotlin code. Although I still can’t write as well as the AI, I’m now confident that I can replicate M1’s functionality without AI’s assistance.
    - Disadvantages: Due to the nature of inquiry-based learning, my current understanding of Android development is still fragmented. If I were to work on a more complex Android project involving the implementation of additional features, I would still be lacking a lot of foundational knowledge and need the assistance of AI.
2. Frontend/Backend development
    - Description: I primarily use code generated by AI models to complete front-end and back-end development.
    - AI interfaces and models used: Codex conversation as interface; GPT-5.6 Luna high, GPT-6 Astra high as models.
    - Strategy: Since I use an interactive learning approach when having the AI generate code, I review each piece of AI-generated code before inserting it into the appropriate location in the project.
    - Advantages: It quickly improved my understanding of Kotlin's features (though my knowledge of TypeScript is already quite extensive, so the improvement was limited) and my ability to review code written by AI. I also believe this approach has improved the overall code quality of my M1 project.
    - Disadvantages: Compared to regular vibe coding, this took me significantly more time.
